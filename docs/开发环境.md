# 开发环境

这份文件说清楚：项目里有哪些工具、各自管什么、为什么这么配、遇到问题怎么办。
给「接手这个项目的人」看，也给 AI 助手看（`AGENTS.md` 管的是业务规则，这份管的是工程规矩）。

## 一、目录结构

```
question-bank-card/
├─ app_launcher.pyw          桌面程序入口（双击运行的 .pyw）
├─ app_window.py             桌面窗口
├─ start_question_bank.py    命令行启动
├─ tiyouju_cli.py            命令行工具（tiyouju --version 等）
├─ dev.ps1                   ★ 开发环境入口（一条命令干一件事）
├─ backend/
│  ├─ core/                  业务代码（Django）
│  ├─ requirements.lock.txt  运行期依赖（锁死版本）
│  └─ requirements-dev.txt   开发期工具（锁死版本）
├─ frontend/                 前端网页（原生 JS，没有构建步骤）
│  ├─ library.js             正式题库页
│  ├─ app.js                 审核录入页
│  ├─ exam-export.js         组卷导出（共享给 PDF/Word）
│  ├─ test_*.js              前端测试（node --test）
│  └─ testdata/              两边共用的取值文件
├─ packaging/                打包（PyInstaller + Inno Setup）
├─ tools/                    运维/验收脚本
├─ .github/workflows/        ★ CI：每次提交跑检查；打标签自动出包发 Release
```

**运行时零依赖**：前端不用打包器、不用框架，浏览器直接跑 `<script>` 加载的文件；
后端依赖 15 个，都锁在 `backend/requirements.lock.txt` 里。

## 二、工具链

### Python 那一侧

| 工具 | 干什么 | 配置在 |
| --- | --- | --- |
| **ruff** | 代码规范：写错的、写漏的、重复的、不安全的写法 | `pyproject.toml` 的 `[tool.ruff]` |
| **ruff format** | 排版统一 | 同上 |
| **mypy** | 类型检查：类型对不对、会不会拿 None 直接用 | 同上 |
| **coverage** | 覆盖率 | 同上 |

**ruff 的规则是挑过的，不是全开。** 刻意放过的：

- `E501` 长行 —— 这个项目里长行多半是中文提示语和 HTML 片段，拆了反而难读；
- `E701` / `E702` 一行多句 —— 紧凑写法（`if x: return`）是这里的风格；
- `UP031` printf 格式化 —— 存量 80 多处，改了是大面积无意义 diff；
- `E402` import 不在文件顶部 —— Django 的 settings 有时要后置导入。

**格式化的行宽定 120**（跟代码原来的习惯一致）。
另外 `skip-magic-trailing-comma = true`：不按「魔法尾逗号」把
「一行放十几个键」的字典拆成一行一个 —— 那样代码会凭空长两万行，
是把代码改难读，不是整理格式。

**mypy 现在查 65 个源文件里的 33 个**（其余 32 个模块还没写类型标注，
在 `pyproject.toml` 的 `[[tool.mypy.overrides]]` 里列着，条数也写了）。
逐条问题记在 [类型检查待办.md](类型检查待办.md)。
其中 `operator` 和 `index` 那两类值得先看：大多是「这里可能是 None，
却直接拿去比较或下标了」—— 真能崩，不是标注洁癖。

### 前端那一侧

| 工具 | 干什么 |
| --- | --- |
| **eslint** | 没定义就用、声明了没用、`==` 用错地方、循环里的坑 |
| **prettier** | 排版统一（**只对单个新文件用，不整体跑，也不设门禁**） |

**为什么前端不做格式门禁**：这一版的前端测试大量是「按源码文本断言」的
（`assert.match(js, /.../)`），格式一改就红一片 —— 实测整体过一遍 prettier
会红 50 条。要真正统一格式，得先把这批测试改成按行为断言，那是另一件事。

eslint 里有两条是按这个项目的实际情况特意调的：

- `no-loop-func` 关掉 —— JS 的 `for (let …)` 本来就每轮一份绑定，
  这条规则在 JS 里几乎全是误报（它是从 Python 的闭包坑照搬来的）。
  真正会出事的是 `var` 循环变量，那个由 `no-var` 挡着。
- `no-irregular-whitespace` 放过注释、模板和正则 —— 中文排版里全角空格（　）
  是故意用的，正则里那几条也全是故意要匹配全角/零宽字符的。

### 依赖怎么锁

- Python 运行期：`backend/requirements.lock.txt`（部署、构建、CI 都用它）
- Python 开发期：`backend/requirements-dev.txt`
- 前端：`package-lock.json`（**要提交**）

工具版本也锁死：工具版本变了，检查结果就可能变，不能让「昨天过的今天红了」。

## 三、三组测试

| 组 | 命令 | 数量 | 管什么 |
| --- | --- | --- | --- |
| 后台 | `python backend/manage.py test core` | 2341 | 业务逻辑 |
| 前端 | `node --test frontend/test_*.js` | 138 | 网页行为 |
| 桌面外壳 | `python -m unittest test_launcher test_backup …` | 145 | 启动器/窗口/凭据/打包 |

> **跑桌面外壳测试前先把题有据关掉。** 程序正在跑的时候跑这组测试，
> 整个测试进程会以退出码 `-1073741510`（缺 DLL 入口点）崩掉，
> 只打出几个点就死 —— 看着像自己的改动弄坏了，其实是程序占着文件。
> 先 `Get-Process -Name 'QuestionBankCard' | ForEach-Object { $_.Kill() }`，跑完再起回来。

## 四、CI 干什么

`.github/workflows/ci.yml`（每次推送、每个 PR）：

1. ruff check → ruff format --check → eslint → mypy
2. 后台测试 → 前端测试 → 桌面外壳测试

`.github/workflows/release.yml`（推 `v*` 标签）：

1. 装 Inno Setup 7
2. 跑上面那整套检查
3. `packaging/build.ps1` 打包（PyInstaller + Inno Setup + 审计 + SHA-256）
4. `packaging/make_release_essentials.py` 组装公开附件
5. 建 GitHub Release 并上传附件

**发版不用再手动一步步来了**：改版本号 → 提交 → 打标签 → 推上去，CI 全包。

## 五、打包

```powershell
.\dev.ps1 build -Version 1.26.26
```

`packaging/build.ps1` 会：

1. 建一个隔离的构建虚拟环境，装锁死的构建依赖
2. PyInstaller 打成 onedir
3. **审计**：检查产物里有没有数据库、试卷、凭据、日志
4. 冻结产物的 `--version` 必须和 `version.py` 对得上
5. Inno Setup 打成按用户安装的安装包
6. 算 SHA-256

产物在 `packaging/dist/`。

## 六、常见坑

- **桌面外壳测试莫名崩**（退出码 -1073741510）→ 题有据还在跑，先关掉。
- **ruff format 报 `Annotation range ... is beyond the end of buffer`** → 那是 ruff
  自己的渲染器在中文文件上的 bug（`ruff_annotate_snippets`），不是代码有问题。
  改用 `ruff format`（写模式）就好；`--check` 只在要显示差异时才触发它。
- **装好的程序打不开 / 改不动** → 别直接改安装目录；改源码、重新打包、装。
- **导出的 PDF 和预览对不上** → 那是真问题：预览和导出必须用同一份内容。
  相关的验收脚本在会话工作区 `check-heading-compare.js`。

## 七、为什么要有这套东西

一句话：**让「改完之后有没有改坏」这件事，不再靠记性。**

- 规范和格式自动查，不用人肉看；
- 类型检查把「可能是 None 却直接用」这类隐患挑出来；
- 三组测试守住业务、网页、桌面三层；
- CI 每次提交都跑一遍，不靠谁记得；
- 发版一个标签走完，不用手动拼十几条命令。

门禁不是形式：它们已经真抓出过问题（一次是标签目录里闭包抓着循环变量，
一次是「去右边面板核对」按钮点了没反应 —— 前端代码里引用了一个不存在的变量）。
