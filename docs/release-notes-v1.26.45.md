# 1.26.45：卡面上印着的章节名，终于真搜得到了

1.26.44 让教材的小节名回到了卡面上。这一版把最后半截接上 ——
**印着的那段字，拿去搜要搜得到**。

## 一、原来是什么样

搜索靠的是入库时算好的那一列索引。改了章节名的规矩以后，**老卡片还存着旧索引**：

- 卡面上印着「第 232 页 · 5.5.2 简单的三角恒等变换」
- 拿「简单的三角恒等变换」去搜 → **一张都搜不到**

老师的感受就是「卡上写着有，搜又搜不着，说不清哪边错了」。

真库实测：1267 张卡里 **318 张**的索引跟现规则对不上。

## 二、原来打算怎么办，怎么改的

上一版留了一条命令，让人手动补：

```
manage.py refresh_search_index --apply
```

但这条命令有个实际问题：**每台机器升级后都会欠一次**。
老师不会去敲命令，欠一次就一直搜不到 —— 问题不会自己消失，
只是从「所有人都遇到」变成「只有记得敲命令的人不遇到」。

所以这一版把补写放进**升级流程**：软件升级时自己补齐。

## 三、现在是什么样

- 升级软件时，这一步自动跑 —— 跟别的数据升级一样，不用人管。
- **只重算搜索索引那一列**：题干、答案、解析、图片、旗标、标签一个字都不动。
- 不重新切题、不调用识读服务、不花额度。
- 判据跟入库时完全同一套（不是另发明一套标准），所以补出来的索引
  和以后新入库的卡是一个样子。
- 升级前照旧自动备份整个数据库（这是原来就有的机制）。
- 重复跑不会重复折腾 —— 算出来跟存着的一样就不动。

那条手动命令仍然留着（`refresh_search_index`），
老师要是改了章节名的规矩，可以自己补一次。

## 四、怎么验的

- **改坏了就废**的检查一共 **8 条，全部被挡住**：
  不写回、写回时漏掉章节名、整段都不写、只补一份资料、
  缺字段的老卡片报错跳过、连题干快照一起覆盖、连标签一起覆盖、判据反了。
  每一条都在临时副本上改坏、跑测试、看它报警、按字节还原后核对哈希。
- 后端 **2466 项**（新增 10 项）全过。
- 真机验：造一份「升级前」的库（索引是旧的），走一遍真实的升级流程
  （退回旧版本 → 升级到新版本），确认索引自动补齐；
  再升一次，确认不重复折腾。
- 老师的真库在补写这一步之前，先整份备份了一份留底；
  补写本身只动搜索索引那一列，题干、答案、图片、标签逐项核对过没变。
