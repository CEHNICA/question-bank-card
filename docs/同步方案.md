## 二、为什么不能"把库丢进坚果云就完事"

坚果云（以及任何网盘）同步的是**文件**，不是"数据库"。题有据的库是一个 SQLite 文件 +
一个数据目录：

```
%LOCALAPPDATA%\QuestionBankCard\
├─ db.sqlite3            52 MB   题库本体（898 道题、869 个入库快照、302 个标签…）
├─ data\                 447 MB  原卷照片/PDF、配图、解析图片
│  ├─ <卷 id>\…
│  ├─ library-solutions\…      答案解析里的图片
│  └─ library\…                题库缩略图
└─ backups\              只存 db.sqlite3 快照（不含原卷）
```

把 `db.sqlite3` 直接放进同步目录有两个硬伤：

1. **两台设备同时开着就可能写坏。** SQLite 靠"一个写锁"保证一致性；网盘同步两个
   副本时，你不知道对方写到了哪一半，合并出来的文件轻则丢一次写入，重则打不开。
2. **网盘的"文件冲突"副本是静默的。** 坚果云遇到冲突会存成
   `db (冲突 20261022).sqlite3`，你不会收到任何提示。用户的题库从此少了一天的改动，
   而且**他自己不知道**。

所以：**库文件不进同步目录。同步的是"题有据自己导出的包"，由题有据负责合并。**
好处是冲突变成明面上的（"有 N 道题两边都有，保留本机的"），而不是静默的。

另外补一句好消息：**现在已经有的能力**——`start_question_bank.py` 里的
`_relocate_local_paths()` 在每次启动时会把库里的绝对路径改到新位置。也就是说
"把整个 `QuestionBankCard` 目录复制到另一台电脑" 现在就能打开用。这是"整目录同步"
这条路的底子（见第八节）。

## 三、方案总览：三层，从稳到巧

| 层 | 名字 | 怎么做 | 适合谁 | 状态 |
|---|---|---|---|---|
| **L1** | **备份包（搬家）** | 题有据导出一个 zip；另一台导入 | 换电脑、备份防丢 | 设计完毕，可先做 |
| **L2** | **并库（合并）** | 导入包时按身份规则合并，本机不丢 | 两台电脑各改了一些 | 设计完毕，可先做 |
| **L3** | **多设备同步（坚果云）** | 题有据在坚果云目录里放"同步包"，两台设备各自推/拉 | 一台电脑改、另一台看见 | 依赖 L1+L2，外加节流策略 |

**建议先做 L1+L2**（一次做完，互相依赖），L3 单独一个版本。

L3 的做法（先把话说清楚，免得做成"云同步"那个坑）：

- 题有据在**指定的同步目录**（比如坚果云的同步文件夹）里维护一个**同步包**文件，
  名字带时间和设备名：`题有据同步-我的电脑-20261022-1530.zip`。
- 每台设备各写自己的包（文件名不同，不会互相覆盖），**谁也不覆盖谁**。
- 「拉取同步」= 把同步目录里**别的设备**写的包按 L2 的规则合并进来。
- 「推送同步」= 把本机当前状态导出一个包写进同步目录。
- **同一时间只在一台设备上打开题有据**（界面里明说），或者接受"后合并的覆盖前面的
  同一字段"这个规则。

这样同步目录里永远是"一堆互不覆盖的包"，坚果云的冲突副本问题就不存在了；
真出现冲突，题有据也能看得见、说得清。

## 四、备份包长什么样

一个 zip，名字 `题有据备份-20261022-1530.zip`：

```
题有据备份-20261022-1530.zip
├─ 题有据备份.json      清单：版本、导出时间、软件版本、每套卷子的身份和题数
├─ 题库.sqlite3         题库本体（用 SQLite 自己的备份接口拍的一致性快照）
└─ 原卷\                原卷照片/PDF、配图、解析图片
   ├─ <卷 id>\…
   └─ library-solutions\…
```

几个关键决定：

- **清单里记相对路径**，不记绝对路径。同一台机器换个位置、另一台电脑不同用户目录，
  导入时都能对上。（库里的 `Paper.source_path` 是绝对路径，导入时要按清单重写。）
- **`题库.sqlite3` 用 `sqlite3.Connection.backup()` 拍**，不是直接拷文件。软件正在用
  的时候直接拷可能拷到一个半写状态的库。现在 `pre-migrate-*.sqlite3` 备份就是这么做的，
  有现成写法。
- **不带渲染页图（`pages\page_N.png`）、不带 MinerU 中间产物（`chunks\`、
  `mineru_result.zip`）、不带 AI 任务队列（`core_libraryjob` 2626 行）和 AI 标签候选
  （902 行）**。这些都能重新生成，带上只是让包变大、冲突变多。
- 体积：现在这台机器 **db 52 MB + 必需品约 60 MB ≈ 110 MB**（不带渲染页图和中间产物
  是 341 MB → 排除后主要是原卷 PDF/照片和解析图片）。

## 五、身份与合并规则

### 5.1 怎么认出"同一样东西"

| 对象 | 身份 | 为什么这么定 |
|---|---|---|
| 试卷 | 原文件内容的 **sha256**（库里已有） | 同一份 PDF/照片就是同一份卷；改个文件名不算新卷 |
| 题 | (卷的 sha256, **题号**) | 题号是老师自己认的编号 |
| 题"是不是同一道" | 题干前 30 字 | 题号一样但题干明显换了 → 不是同一道题，不覆盖 |
| 标签 | 名字 + 类型（库里有唯一约束） | 同名同类型 = 同一个标签 |
| 标签上下级 | (子, 父, 关系类型)（唯一约束） | |
| 题上的标签 | (题, 标签)（唯一约束） | 取并集 |
| 答案解析 | 归属的入库版本 | 解析是跟着题目走的 |
| 入库快照 | 归属的题 + 版本号（唯一约束） | |

**这些唯一约束是现成的**（`unique_library_tag_name_kind`、
`unique_library_tag_relation`、`unique_publication_tag_assignment`、
`unique_block_seq`、`unique_question_version`），所以合并天然幂等：同一个包合并两次，
第二次什么都不会变。

### 5.2 合并时到底怎么合

**同一份原卷**（sha256 相同）：

- **本机没有这套卷** → 整卷搬进来（题、配图、标签、解析全带）。
- **本机有这套卷** → 逐题比：
  - 本机这道题**没写答案/解析**，备份里有 → **用备份里的补上**。
    （最常见的场景：学校电脑上补了解析，家里合并后就有了解析。）
  - **两边都有** → **保留本机的**，报告里点出来："有 N 道题两边都有，保留了本机的版本"。
  - 本机**没有这道题** → 整道题搬进来。
  - 题号一样但题干明显不是同一道题 → **两道都留着**，报告里点出来，不覆盖。
  - 标签 → 取并集。
  - **入库/通过状态不动本机的**——"通过"是人的决定，合并不替人做主。但会告诉老师：
    "那边有 N 道题已通过入库，本机还没通过"。

**报告长这样**（要像人话，不能像字段名）：

> 合并完成。
> 新增 3 套卷子、405 道题。
> 给本机 12 道题补上了答案和解析。
> 有 45 道题两边都有内容，保留了本机的版本。
> 有 2 道题题号一样但内容不同，两道都留着了。
> 标签合并了 18 个，7 道题多贴了标签。
> 本机原有的题一道没删。
> 想撤销？见"导入记录"。

### 5.3 撤销

每次合并都写一份**导入记录**（JSON，放在数据目录里），记下"这次新增了哪些卷/题/标签"，
并给一个「撤销这次合并」入口。撤销 = 精确删掉这些行 + 这些文件。
（不用数据库快照回滚——那会把老师在这期间新做的活儿一起抹掉。）

### 5.4 导入前先看一眼

合并前先给一张"会发生什么"的卡片：

> 这份备份：2026-10-22 15:30 导出，8 套卷子、807 道题
> 本机现在：5 套卷子、402 道题
> 合并后：预计 8 套卷子、807 道题（新增 3 套 405 道；补上 12 道题的答案；45 道题保留本机版本）

然后老师点「合并进来」才真的动。

### 5.5 核心规则已经用原型验过

用两个**独立**的库（模拟两台电脑）、同一份原卷（sha256 相同）、各三道题，
跑了一遍导出→合并→再合并：

```
机器 A： 1 套卷  [(1,'甲'), (2,'空'), (3,'空')]
机器 B： 1 套卷  [(1,'乙'), (2,'丙'), (3,'丁')]

第一次合并： 补上答案 2、两边都有保留本机 1
第二次合并： 补上答案 0、两边都有保留本机 3   ← 再合一次什么都没变（幂等）

机器 A 合并后： 1 套卷  [甲, 丙, 丁]
```

三条要命的规则都成立：同一份原卷认得出是同一套卷（不会变成两套）、本机空着的答案
被补上、两边都有的保留本机的、合两次结果不变。

**还没验的**（写代码时要补测试）：标签并集、入库快照、答案解析图片、绝对路径重写、
原卷文件搬运、撤销记录、界面。

## 六、界面（设置 → 新增一节「数据备份与迁移」）

设置现在有四区（API 配置 / 显示与导出 / 帮助 / 关于），加第五区：

```
数据备份与迁移
题库全在这台电脑上。换电脑、备份，或者把两台电脑的题库并到一起，都在这里。

[导出备份]     选一个文件夹，题有据把整库（含原卷）打成一个包放进去
[从备份合并]   选一个备份包，先看会发生什么，确认后合并进来
[同步目录]     （L3）指定坚果云之类的同步文件夹，题有据在这里放同步包
[导入记录]     每次合并的记录，可以撤销最近一次
```

每个按钮都要有**说人话的结果**：

- 导出后：「已导出：8 套卷子、807 道题，110 MB（含原卷照片）。文件在 D:\备份\…」
- 合并后：上面那份报告。
- 出错时：说清是哪一步不行、下一步点哪里。**不能出现"请重试"这种死路。**

## 七、安全边界

- **只认自己导出的包**：清单里有包格式版本和校验和；不认的包直接拒。
- **解包不越界**：不接受绝对路径、不接受 `..`、不跟随符号链接（照抄
  `native_folder_picker` / `library_solutions` 里已有的那套校验写法）。
- **导入前自动快照**当前库到 `backups\pre-import-<时间>.sqlite3`（`backup()` 接口，
  和 pre-migrate 备份同一套）。
- **全程一个事务**：中途失败整体回滚，不会合到一半。
- **只增不减**：合并永远不删本机已有的题。
- **不联网、不上传、不碰密钥**：包里只有题库和原卷；API 密钥、设置、任务队列都不进包。
- 大小上限：包超过上限（比如 2 GB）直接拒并说清楚。

## 八、多设备同步（坚果云那条路）具体怎么做

前提：题有据**不把库文件**放进同步目录，只放"同步包"。

1. 老师选一个同步目录（就是坚果云的同步文件夹）。
2. 题有据在这里维护 `同步包-设备名-时间.zip`，**每台设备各写各的**，文件名不同，
   坚果云不会判成冲突。
3. 「推送同步」= 导出当前状态写进同步目录（也可以每次改动后自动推）。
4. 「拉取同步」= 扫同步目录里**别的设备**写的包，按第五节的规则合并，出一份报告。
5. 老师点「同步」这一个动作 = 推 + 拉 + 报告。

要额外说清的话（写进界面）：

- **同一时间只在一台设备上打开题有据**。两台同时改同一道题，合并时按"保留本机"
  处理——不丢数据，但有一边的改动要等下一轮同步才看得到。
- 同步目录里的包会越积越多 → 题有据自动只保留最近 N 个（比如 10 个），其余自动清理。
- 原卷照片/解析图片体积大 → 同步包里只带必需品（见第四节）。

**另一条更省事的路**（不用坚果云也行）：直接把整个
`%LOCALAPPDATA%\QuestionBankCard` 目录放进同步目录。`_relocate_local_paths()` 会在
启动时把路径改到新位置，所以复制到另一台电脑照样能用。**但这条路有第二节说的两个
硬伤**（同时写、冲突副本静默），只能当作"知道风险的人自己选"的备选，不能当推荐做法。

## 九、实施顺序

| 步 | 内容 | 产出 |
|---|---|---|
| 1 | 备份包导出（清单 + 一致性快照 + 原卷） | 「导出备份」能用 |
| 2 | 导入前的预览 + 合并规则 + 报告 + 撤销 | 「从备份合并」能用 |

| 5 | 同步目录 + 推/拉 | 多设备同步 |

第 1、2 步做完，"搬家 + 并库"就齐了——这正是群里提的两件事。
第 5 步是"类似坚果云"那条。

## 十、需要拍板的三件事

1. **两边都有答案时保哪边？** 我建议**保本机的**，报告里点出来，让老师自己去另一边改。
   （另一条路是"保新的"，但"新"要看机器时间，跨机器不可靠。）
2. **要不要"用备份整个替换本机题库"这个模式？** 我建议**先不做**：合并已经覆盖搬家场景
   （新电脑上是空的，合进去就等于搬过去了），而"替换"是不可逆操作，风险高。
3. **自动备份留几份、放在哪？** 我建议：每周一份、留最近 10 份、放
   `%LOCALAPPDATA%\QuestionBankCard\backups\`（不主动往网盘里塞东西）。
