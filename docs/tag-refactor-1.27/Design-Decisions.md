# Design-Decisions.md —— 模型、查询、迁移与兼容决策

依据：《题有据-标签系统重构执行计划》第 3～7 节。
日期：2026-10-25。

---

## 0. 一句话

**复用并扩展既有模型，不建第二套账；用途记在关联上，不记在概念上；范围落成非空字符串键，因为 SQLite 的 NULL 不参与唯一约束。**

---

## 1. 数据模型决策

### 1.1 复用还是新建

计划第 4 节要求「优先复用和扩展既有模型」「可以合并存储语义兼容的对象，但外键、范围、状态与审计约束仍须可验证」。

既有模型已经覆盖了不少：`LibraryTag`（词条）、`LibraryTagRelation`（上下级）、`LibraryTagCatalogue`（修订号）、`LibraryTagAssignment`（贴标）、`LibraryTagSuggestion`（AI 候选）、`LibraryTagOperation`（操作历史与撤销）、`LibrarySolution`（解析版本）。

**决策：扩展，不新建平行表。** 新增 12 张表，其中 10 张是新领域（教材目录、专题、小问、解法分支、依据、整理程度、保存搜索、迁移映射），2 张是把既有对象分出语义（`LibraryCollection` 专题、`LibraryCollectionMember` 专题成员）。

理由：既有 `LibraryTagAssignment` 已经是「一道题上的正式关联」，再新建一张 `assertion` 表就变成两套账 —— 老师改了一处、检索读另一处，最后没人知道哪个是真的。计划第 7.4 节明确要求「单一正式写入入口」。

### 1.2 概念身份：拆掉「名称＋互斥类型」

**旧**：`LibraryTag` 的唯一约束是 `(kind, name)`，`kind` 是 `knowledge / method / custom / legacy` 四选一。

**问题**：「分类讨论」当考点还是当方法是**用途**问题，不是概念身份问题。旧结构逼着系统为同一种数学内容建两条记录，于是「同一个分类讨论」在考点目录和方法目录里各有一个，跨不过去。

**新**：

| 字段 | 作用 |
|---|---|
| `canonical_key` | 规范名的归一化形式，**全库唯一**（条件唯一索引：`canonical_key != ""`） |
| `scope_note` | 范围说明。同名但含义不同时用它区分，界面显示，不自动合并 |
| `type_hints` | 类型提示**多值** JSON，只用于推荐和浏览 |
| `merged_into` | 合并后的重定向目标。旧 ID 保留，历史名称与引用可追溯 |
| `kind` | 保留，但**不再参与唯一约束**，也不再决定身份 |

唯一约束从 `(kind, name)` 改成 `canonical_key` 单独唯一，条件是 `canonical_key != ""`。

**为什么用条件唯一索引而不是普通唯一**：`canonical_key` 允许为空（尚未回填的旧记录），而 SQLite 视所有 NULL 互不相等 —— 用普通唯一约束的话，NULL 行不会互相冲突，但非空行会。更要紧的是：**空字符串在普通唯一约束下会互相冲突**，所以条件写成 `!= ""`。

### 1.3 归一化：`concept_key`

放在 `backend/core/textnorm.py`（那是这个项目「文本归一化」的家），因为**迁移回填和运行时必须算出同一个结果**，否则迁移后新旧两套对不上号。

规则：NFKC → casefold → 去所有空白 → 去中文标点（`，,。、；;：:！!？?·…—–"'""''《》〈〉`）。

**数学符号一律不动**：`a-b ≠ ab`，`f(x) ≠ fx`。

明确的取舍：**不去掉括号**。`中位线定理（性质）` 和 `中位线定理` 归一化后不同 —— 这是对的，它们含义确实不同。想靠去括号并掉，那是替用户做数学判断。

`中位线定理` 与 `中位线 定理` 归一化后相同 —— 这也是对的，它们是同一个概念。

**迁移文件里另写了一份等价实现**：历史迁移不该依赖会变的应用代码。Django 的最佳实践如此，代价是要有一处重复，测试里断言两边一致。

### 1.4 关联：从「题＋标签」到「题＋标签＋用途＋范围」

**旧**：`UniqueConstraint(publication, tag)` —— 一道题上同一个标签只能有一条。范围塞在 `scope` JSON 里，而 `_clean_scope` 把它的合法取值限死：知识点必须 `{"whole": true}`，方法只能是 `{"whole": true}` 或 `{"subquestions": ["1", "2"]}`。

**问题**：同一个方法在小问 1 和小问 2 各用一次，存不下；「第（1）问可用中位线」和「整题可用中位线」也存不下（那会互相覆盖）。

**新**：

```
UniqueConstraint(publication, tag, role, scope_key)
```

- `role`：主要考查 / 辅助用到 / 解法采用 / 题面特征 / 旧关联（作用未细分）
- `scope_key`：规范化范围键，**非空字符串**

`scope_key` 的取值：

```
whole                            整题
sub:<小问ID>                     某个小问
variant:<分支ID>                 某个解法分支
sub:<小问ID>+variant:<分支ID>    某小问的某解法
```

**为什么不用 NULL**：计划第 4 节约束 3 点名了这个陷阱。SQLite 认为 `NULL != NULL`，唯一约束对含 NULL 的行不生效 —— 那整题记录就能重复插。

**为什么同时保留 `scope` JSON**：老数据在 `scope` 里，新的结构化引用在 `variant` / `subquestion` 两个外键上。`scope` 保留原样，不删不改 —— 首轮迁移不删旧内容。

**用途为什么是枚举而不是自由字符串**：界面要按用途分组显示（「主要考查」和「辅助用到」在默认视图里显示位置不同），自由字符串做不了这个分组。

### 1.5 小问：稳定 ID vs 展示编号

计划第 3.4 节要求「小问具有稳定 ID，展示编号只是标签；重排后不能仅靠字符串『1』继续绑定」。

**新模型**：`LibrarySubquestion`（`stable_key` 唯一、`display_label` 可变、`locator` 定位）。

既有系统怎么表示小问的？`qtypes.subquestion_labels(stem)` 从题干文本正则认 `(1)(2)`，但只用于判断题型和显示计数，**标签侧的小问只是 `scope` 里的字符串数组**，不落任何独立结构。

所以 `ensure_subquestions()` 从题干拆小问，落库时给的是 `stable_key = "sq:1"` 这种稳定键。以后小问重排，显示编号变了，稳定键不变，绑定不会跟着跑到别的小问去。

**拆不出就不拆**：题干没有可靠小问标记时按整题记录，不虚构编号。

### 1.6 解法分支

既有 `LibrarySolution` 是**线性版本链**（`parent` 自引用 + `extras["solution_id"]` 指针），不是分支树。全库 grep `variant|branch|分支` 在 `backend/core` 的命中全是无关物（配图槽位、读图请求变体）。

**新模型**：`LibrarySolutionVariant`（分支）+ `LibrarySolution.variant` 外键（把某版解析挂到某个分支下）。

分支来源分三类：原卷解法 / 教师保存解法 / 已确认的其他解法。

**界面写「已记录的其他解法」，不写「所有解法」** —— 没有任何一套流程能证明已经穷尽一道题的全部解法。计划第 3.4 节最后一句就是这条。

### 1.7 教材目录与概念分离

`LibraryTextbook`（教材版本）+ `LibraryChapter`（章节）+ `LibraryChapterConcept`（章节↔概念）+ `LibraryQuestionPlacement`（题目↔章节）。

**教材关联分两种，不互相冒充**：

| 关系 | 含义 |
|---|---|
| `source` 来源位置 | 这题确实出自那本书那节 |
| `teaching` 教学对应 | 这题适合在某节讲，或该概念在那节出现 |

由「函数单调性在某教材某章出现」不能反推所有单调性题都出自该教材。

**章节的规范化键 `node_key`**：SQLite 的 NULL 不参与唯一约束，「无教材的顶层章节」用 `(textbook=NULL, parent=NULL, title)` 拦不住重复。所以整条父子链落成一个非空串：

```
generic:<title>                  通用教学目录下的顶层章节
tb:<textbook_id>:<title>         某教材下的顶层章节
...:<parent_id>:<title>          下一层
```

### 1.8 专题独立

`LibraryTagGroup` 是**标签的分组**（0028 迁移后已被搬成 hierarchy 关系，正向写入口已删，是半死状态），语义不是「题目的集合」。

所以新建 `LibraryCollection`（个人专题）+ `LibraryCollectionMember`（成员，只存引用不复制题面）。

一道题可以同时在两个专题里；移出专题不删题。

### 1.9 整理程度

`LibraryCoverage`（题 × 范围 × 用途维度 → 未整理 / 已检查 / 部分检查 + 检查依据）。

**为什么必须有**：没有它，「未贴标签」和「确认过没有」分不开。计划第 6.4 节讲排除条件时说了最要命的一句 —— 排除一个方法时，未知不能当成「确实没有」。

### 1.10 依据

`LibraryAssertionEvidence`（指向题面版本、相关解析版本、关键片段 + 定位 + 快照摘要）。

计划第 3.5 节：「不要只存一段与原文脱离的 AI 总结」。所以依据要能回跳。

### 1.11 核对状态与依据有效性分开

计划第 3.5 节：「不要用一个真假字段同时表达『人工确认过』和『仍适用于当前题面』」。

所以两个字段：

| 字段 | 取值 | 含义 |
|---|---|---|
| `review_status` | 候选 / 已确认 / 已拒绝 / 已归档 | 人怎么处理的 |
| `evidence_status` | 当前有效 / 需复核 / 旧记录未绑定具体依据 | 还成不成立 |

`needs_review` 布尔位保留（旧代码在用），但不再是唯一真相。

### 1.12 约束总表

| 约束 | 怎么落地 |
|---|---|
| 概念身份不依赖「名称＋互斥类型」 | `canonical_key` 条件唯一索引，`kind` 退出约束 |
| 关联唯一性含范围、用途、解法分支、适用解析版本 | `(publication, tag, role, scope_key)` |
| SQLite NULL 唯一性语义 | 范围键、章节键都是**非空字符串**，没有 NULL |
| 小问、解法、证据必须属于同一题目版本 | 服务层 `_same_publication()` 跨题绑定直接拒绝 |
| 分类上下级不允许循环 | `_creates_cycle()` 在建关系前查；`CheckConstraint(~Q(parent=F("child")))` 挡自环 |
| 规范化名称冲突产生可处理的歧义 | 归并历史标签；两个正式概念同名则各自保留并标歧义 |
| 合并保留旧 ID 重定向 | `merged_into` 外键 + `LibraryMigrationMap` |
| 新建目录节点、收起地图、改变排序、搜索不写正式关联 | 这些操作全部不在服务层写路径里 |
| 修订冲突保护、幂等请求 | 沿用 `PublishedQuestion.tag_revision` CAS + `LibraryTagOperation.client_request_id` |
| 归档优先于破坏性删除 | 停用用 `active=False`，不删 |

## 2. 查询语义决策

### 2.1 三层分区，不是两个

| 分区 | 判据 | 计入正式匹配数？ |
|---|---|---|
| 已确认匹配 | 存在满足条件、依据当前有效的正式关联 | **是** |
| 旧标签命中 | 有旧记录，但没绑定到具体依据 | **否**，单独计数 |
| 待核对线索 | 有 AI 候选或全文提及 | **否**，单独计数 |

返回结构：`count`（已确认匹配）、`total_count`（含旧记录）、`legacy_count`、`clue_count`、`unknown_count`、`excluded_count`。

### 2.2 方法 A 与方法 B 默认同解法 AND

`cooccurrence` 默认 `same_variant`：按解法分支分组，同一分支内要集齐全部方法。要找「分别有两种解法」的题得显式写 `separate`。

**为什么要默认这么严**：暗中混用两种语义，搜出来的题会让老师白翻。计划第 6.3 节原话。

### 2.3 概念条件只认已确认的关联

`_concept_group_match` 里 `_is_confirmed(row)` 是硬门槛。未核对的候选不是正式匹配。

「包含下级」用 `expanded` 映射（每个被问的概念 → 自身 + 下级），**只扩展检索范围**：不给题目复制父级标签，也不表示题目考查了父概念的全部性质。

### 2.4 排除条件的三态

`_exclusion_state()` 返回 `hit` / `legacy` / `unknown`：

- `hit`：确认用过 → 排除掉
- `unknown`：没整理、依据需复核 → **单独计数，不当作「确实没有」**
- `handling_of_unknown = "separate"`（默认）：未知单独计数并给入口
- `handling_of_unknown = "exclude"`：未知也排除（用户明确要）

### 2.5 命中原因

每条结果带 `reasons[]`，每条有 `kind`（concept / method / legacy）、文字说明、涉及的标签 ID 和范围键，界面可以点进去看依据。

### 2.6 「已确认匹配」的三个条件，缺一不可

`review_status == 已确认` **且** `needs_review == False` **且** `evidence_status == 当前有效`。

第三个条件是后补的。原来只查前两个 —— 结果旧记录（`evidence_status = 未绑定具体依据`）
和需复核的记录会被算进「已确认匹配」。这跟计划第 3.5 节直接冲突：
「人工确认过的旧记录不能因为迁移失败就被说成『从未确认』」，反过来也一样 ——
**依据已经不成立了，就不能还说它「已确认」**。

SQL 层的候选集用的是同一组条件（`_CONFIRMED_SQL`），两边不能各说各的。

### 2.7 关键词：多个词是「各自出现」，不是「整串连续」

**这是本轮改掉的一个语义**，写在这里备查。

原来：把所有关键词拼成一个整串，要求它在 `search_text` 里**连续出现**。
所以搜「三角 函数」搜不到题面里写着「三角函数」的题 —— 老师明明打了两个词，却因为
中间少一个空格就什么都搜不到。

现在：每个关键词各自在题面里出现即可（AND）。

这个改动也是性能优化的一部分 —— 过滤下推到数据库，不再在 Python 里逐题扫题面。

### 2.8 空条件时报「一共多少题」，不报「已确认匹配 N 题」

空条件时全部题都是结果。但「已确认匹配 / 旧记录 / 未整理」这三个桶要靠逐题查关联
才算得出来，一万道题全查一遍要好几秒，而界面只看得到前 50 道。

所以空条件时只算要显示的那批，统计报**总数**，细分桶给 `null`。前端据此显示「共 N 题」。

**把没查过的说成「已确认」是骗人。** 有条件时桶照常细分（候选集已经很小了）。

### 2.9 候选集先在库里收敛

概念和方法条件都能在 SQL 层算出「哪几道题可能相关」。先算出候选集，再只对这些题做
精确判定 —— 一万道题里挂着一个概念的可能就三十道，那三十道才值得细看。

精确判定仍在 Python 侧（`_concept_group_match` / `_method_group_match`），语义没变；
SQL 层只是把范围缩小了。

**实测**：10,000 题时最慢一条 P95 从 5995 ms 降到 158.5 ms（验收目标 ≤ 500 ms）。

### 2.6 保存搜索存条件，不存结果

`LibrarySavedSearch` 存 `query_version` + 完整条件 JSON。

**为什么不存结果列表**：条件变了结果就该跟着变。存结果等于把「当时的快照」当成「现在的答案」。

**旧保存标签组合怎么办**：旧的是浏览器 `localStorage` 里的 `{name, filter:{mode, all, any, not}}`，后端零命中。本次新增了服务端实体，旧 localStorage 数据仍在原处可用 —— 两套并存期间，旧组合在前端继续按老逻辑用，新保存的走服务端。**这一条尚未做转换**，见 `Known-Issues.md`。

### 2.11 范围要落两处：范围键 **和** 小问外键

一条关联说「用在第（1）问」，要写两个地方：

| 字段 | 作用 | 写错的后果 |
|---|---|---|
| `scope_key`（`sub:<uuid>`） | 唯一性约束的一部分；同一题上同一个概念在不同小问各记一条 | 范围不同的两条被当成同一条，第二条被唯一约束挡掉 |
| `subquestion_id` | 检索时认「落在哪一问」的那一头 | **这条关联在按小问检索时永远搜不到** |

**为什么两个都要写**：范围键是**串起来的标识**（可能同时含小问和解法分支），小问外键是**检索直接读的那一头**。只写范围键，检索侧 `_scope_matches()` 判 `subquestion_id is None` 就直接返回 False —— 数据在库里、界面也显示「用在第（1）问」，但搜「第（1）问用的方法」就是搜不到。

**这条是实测踩出来的**：先写了范围键，忘了写外键，测试直接报 `None != UUID(...)`。

### 2.12 建议说落在多个小问 → 拆成多条，不拼成一个键

`sub:<uuidA>+sub:<uuidB>` 这种键看着紧凑，但 `parse_scope_key()` 拆回来只会认到最后一个 —— 键里塞了两个小问，等于只有一个能用。

**做法**：一个建议落在几个小问，就落几条关联，每条只带一个小问外键。完整范围仍然留在 `scope` JSON 里（`{"subquestions": ["1","2"]}`），信息不丢。

### 2.13 题上已经有同一个概念时，采纳建议要「另加一条」，不是「当作没这回事」

**旧做法**：找已有行时只按 `(题, 标签)` 找，拿到哪条算哪条。结果是 —— 题上已经有「这个方法用在解法一」，AI 建议说「这个方法用在第（1）问」，找到那行发现不是待核对的，**什么都不做**，但建议被标成「已采纳」。老师看着像采纳了，库里什么都没多。

**新做法**：

1. 先找同一标签下**待核对**的行 —— 那是给这条建议留的槽位，复用它；
2. 没有，再找**用途和范围键都对得上**的正式行 —— 对得上就认它是同一条，不动它；
3. 都没有，**新建**一条。

第 2 步是关键：按 `(题, 标签)` 找会把落在别处范围的行也当成同一条。

### 2.14 「解析版本有没有变」只有一个定义

方法建议要记下它依据的是哪一版解析（`method_source`），采纳时要核对这一版还在不在。

**关键在于「比什么」**：只比 `source` / `solution_id` / `publication_id` / `analysis_hash` / `image_hashes` 这五项 —— 够判断解析有没有被改过，又不会把整份解析原文和图片 base64 塞进数据库。

**这段逻辑以前散在六个地方各抄一遍**（`library_assistant.py` 两处、`library_jobs.py` 四处、`library_tagging.py` 一处）。抄漏一项、抄错一项，就会出现「解析一个字都没改，却说建议过期了」—— 老师看到的是一句没头没尾的「已过期」。

**现在**：`library_tagging.method_source_snapshot()` 负责取，`library_tagging.method_source_matches()` 负责比，六处全走这两个函数。

**而且比对时两边都只取那五项**：存进去的快照可能还带着别的字段（老数据、手工造的验收数据），拿全量去比会把「一样的」判成「变了」。

**这条是实测踩出来的**：造验收数据时存了整份解析快照，采纳时被判「解析版本已变化」，建议直接变 stale。

## 3. 自然语言入口决策

`backend/core/library_nlquery.py`：**不是自然语言理解，是一张有限的规则表加一本本地词典。**

支持：用途词、小问（`第（1）问` / `第一问`）、解法（`解法一` / `另一个解法`）、排除词、题型词、词典里的概念和方法名。

退化行为（比能力更重要）：

1. 认不出的词 → 进关键词，走全文检索；
2. 认出来但不确定的 → 转成需要老师选的条件，不替他定；
3. 词典里一个都没有 → 全部当关键词，并说清楚「本地只认这几种说法」。

`supported_phrases()` 把支持的表达列出来，界面能看。

**没有 API key 也能用** —— 转换纯本地，不调任何外部模型。

## 4. 兼容决策

### 4.1 旧投影继续走

`library_tagging._sync_projection()` 把正式关联投影回 `extras["tags"]` 和 `tags_text`。新系统的关联写入**也调它** —— 旧界面、旧筛选、组卷、导出因此不用改就能继续工作。

**已知折衷**：投影不区分用途，所以「辅助用到」的概念也会出现在旧标签列表里。新界面按用途分组显示，旧投影保持原样。这是「不建立第二套账」的代价，写在这里备查。

### 4.2 旧 CLI/MCP 边界不变

计划第 8 节：「旧『按名称提交标签』的入口仍提交候选」。

本次**没有改动** `library_tagging.resolve_suggestion()` 和 `normalize_ai_output()` 的旧协议 —— 旧入口的行为完全不变，仍是候选协议。

新系统的关联写入走 `/api/library/assertions`，**必须**给出用途和范围；缺 `role` 或「解法采用」缺 `variant_id` 直接报错，不编造。

### 4.3 本机访问限制与来源校验不动

`_guard()`（`X-QB-Request: 1` + `application/json`）、敏感端点的 `REMOTE_ADDR` 检查、凭据的 DPAPI 存储与「不因查看而回填」规则 —— 全部原样保留。新端点全部调用 `_guard()`。

### 4.4 旧关系类型只加不改

`LibraryTagRelation.Type` 新增 `related`（相关／使用）。`hierarchy` 和 `related_method` 原样保留。

相关关系**不参与父级继承**，独立显示。

## 5. 迁移决策

### 5.1 三段式

```
plan_migration()    只算不写（dry-run）
apply_migration()   按批次写，幂等，重复执行不重复建实体
verify_migration()  核对迁移前后的业务不变量
```

**为什么不用 Django migration 做数据搬迁**：Django migration 不可 dry-run、不可重复演练、报告形态不可控。计划第 7.4 节要求「先完成虚构旧库与新库的 dry-run、apply、verify、重复执行和故障恢复」—— 这需要的是一个工具，不是一个一次性脚本。

Django 迁移 `0030_tag_system_refactor` **只改结构**，不搬数据。

### 5.2 章节容器的识别依据

计划第 7.2 节：「章节识别不能仅靠名称前缀；结合系统来源键、原分组、说明、关联结构等证据」。

**判据：`system_key` 以 `section:` 开头**。

这是 0028 迁移留下的系统来源键（`LibraryTagGroup` → 章节标签时打的）。读 1.26.29 迁移前的备份库，库里 17 个章节容器全部带这个前缀（13 个 knowledge + 4 个 method）。

用户自己建的标签 `system_key` 是 `knowledge:正数与负数` 这种，**不带** `section:` 前缀 —— 靠名字像章名（「函数」）不会被误转走。

**版本未知 → 「通用教学目录／版本未指定」**，`LibraryTextbook.unspecified = True`。不编造教材版本。

### 5.3 状态不升级

| 旧内容 | 新处理 |
|---|---|
| 旧知识点正式关联 | `role = legacy`（旧关联，作用未细分），**不自动升级成「主要考查」** |
| 旧方法正式关联 | 有可靠题面＋解析＋范围证据才 `CURRENT`；否则 `UNBOUND`（旧记录未绑定具体依据） |
| 历史未核对标签 | 保持原审核状态；迁移本身不使其正式生效 |
| AI 候选 | 一条不动。逐条决策、依据、版本、草稿、拒绝记录都留着，不自动采纳 |
| 不明确的上下级 | 保留，标 `source = legacy`，不参与新语义推断 |
| 别名及近似名称 | 生成建议映射，不自动做语义合并 |
| 自定义标签 | 按实际内容决定，歧义项等人工决定（记 `needs_review`） |

**「可靠依据」的判据收紧**：人工确认 + 写了理由 + 有对应的解析版本。读 1.26.29 迁移前的备份库：21 条正式关联的 `scope` **全部**是 `{"whole": true}`，且没有一条绑定了解析版本 → 全部判为 `UNBOUND`。

### 5.4 重名处理

读备份库实测：306 个标签里，归一化后重名的只有 **1 组** —— 「平面向量的应用」同时有 `knowledge` 和 `legacy` 两条。

- 历史标签（`legacy`）撞上正式概念 → **归并到正式概念**，旧 ID 保留（`merged_into`），记 `converted`；
- 两个都是正式概念 → **不自动合并**，各自保留、标 `ambiguous`、等人工决定。

### 5.5 幂等与恢复

- 批次号 `LibraryMigrationMap.batch` 唯一键 `(batch, old_kind, old_key)` → 同一批次重复执行走 `update_or_create`，不重复建实体；
- 全程包在**一个事务**里 → 中断即回滚，不会留下半截状态；
- 回填 `canonical_key` 前先查该键是否已被别的概念占用（迁移前用户新建了同名概念的情况）→ 占用则标歧义，不覆盖。

### 5.6 候选状态不被篡改

备份库里 904 条候选：`pending` 443 / `queued` 367 / `stale` 49 / `failed` 38 / `accepted` 7。

**迁移不改任何候选的状态**。`queued` 的 367 条是「排队中、从未真正生成过」，迁移报告里明确写出来，**不替用户触发生成**，也不算成「待核对」。

迁移不 bump `taxonomy_revision` → 候选不会因为目录修订号变化而无差别失效。
